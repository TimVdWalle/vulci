# Project Vision

## Purpose

This project exists to create a programming language that genuinely deserves to exist.

It is a hobby project, but its ambition is not to create a toy language, an experiment, or a proof of concept. The goal is to create a real, general-purpose programming language that people can justify using.

If the language ultimately does not provide sufficient value to justify its existence, it should be considered unsuccessful as a language, even if the project itself remains a valuable learning experience.

The goal is not to invent something different for the sake of being different. The goal is to build a language that is internally consistent, pleasant to use, and capable of solving real-world problems through its overall design.

## Hobby Project vs. Language Goals

The fact that this is a hobby project influences **how the language is developed**, but not **what the language is intended to become**.

Development will be incremental and practical. Early versions will intentionally contain only a small subset of the intended language. Many important features will be implemented much later, not because they are considered less valuable, but because building the language step by step makes the project achievable and enjoyable.

The implementation order reflects practical development priorities, not the long-term importance of language features.

Throughout development, the language should always be designed as if it were intended to become a serious production programming language. Temporary implementation constraints should not unnecessarily compromise the long-term design.

## Relationship to the Philosophies

The language is guided by three core philosophies:

- **Phi1** — One mental model for working with data, regardless of its source.
- **Phi2** — Code should be easy to read and unambiguous.
- **Phi3** — A small set of language building blocks should become powerful through combination.

These philosophies are the primary decision-making framework for the language. Every language feature should support one or more of them.

## Evolution

The language is expected to evolve.

Breaking changes may be acceptable while the language has a small user base. As adoption grows, backward compatibility becomes increasingly important.

Deprecation decisions should be made on a case-by-case basis, balancing the benefits of improvement against the cost of maintaining compatibility.

The scope and philosophy of the standard library are intentionally left undecided and should evolve together with the language.

## Scope

The language is intended to become a general-purpose programming language.

Early development will primarily focus on backend software and small personal applications, but the language itself should not be designed exclusively around those use cases.

## Governance

If the project grows beyond a single developer, the language should eventually be maintained by a small core team.

The community should influence the language through discussion, experimentation, and feedback.

Whenever possible, decisions should be made by consensus. If the core team is evenly divided, the original language designer may act as the deciding vote.

## Success

The success of the project and the success of the language are not the same.

### Successful Project

The project is successful if it remains enjoyable, sustainable, and provides valuable experience and knowledge throughout its development.

Even if the language ultimately does not justify its existence, the project itself may still be considered a success.

### Successful Language

The language is successful only if it genuinely deserves to exist as a programming language.

It should provide sufficient value that experienced programmers can justify choosing it over existing alternatives.

The language should earn its place through the quality, consistency, and usefulness of its overall design rather than through novelty alone.
